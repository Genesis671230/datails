### The demonstrable loop (on the placeholder AQ fixture, Bitcoin)

Victim wallet in → Crystal replay enrichment → FIFO proposes
victim→intermediary (0.45 BTC, confidence 0.95) → investigator confirms →
FIFO proposes intermediary→exchange (0.44 BTC, `boundary_flag=hot_wallet`,
Binance label with data_ledger provenance) → investigator confirms →
traversal ends, run recommends **exchange_information_request** ("last
transaction hash into the hot wallet; next step is an information request,
not further graph traversal") → explorer graph: 3 nodes with label
provenance, 2 confirmed edges with confidence → every step in the ledgers
(2 approval events, ≥4 data_ledger snapshots).

### Design decisions

- **FIFO is engine arithmetic** (`services/traces/fifo.py`), not model work.
  Confidence is a documented deterministic heuristic (0.95 single candidate,
  0.75 ambiguous). Attribution method is configuration (05 §8).
- **LD-27 state machine**: transitions recorded (from/to/cause/timestamp) in
  `workflow_agent_runs.output_ref_json`; `awaiting_confirmation` has no
  timeout; proposal failure → `failed` with confirmed hops intact.
- **Resume-from-last-confirmed**: re-POSTing confirm on the last confirmed
  hop retries the proposal only. Tested: connector outage mid-loop, then
  recovery — exactly one ledger event for the confirmed hop.
- **Boundary detection**: counterparty enrichment (risk check) runs inside
  the proposal step; an entity label or `hot_wallet` kind marks the hop and
  ends traversal on confirmation.
- **Graph in `GET /traces/{id}`**: the canonical route list has no separate
  graph endpoint, so the explorer payload rides the trace detail (nodes =
  wallets with current labels + provenance; edges = confirmed hops).
- **Tracked amount**: until the real AQ dataset defines the stolen amount,
  the engine tracks from the first candidate (`min(tracked, transfer)`).
  The real dataset slots in as fixture data, no code change.
